# Independent DB sessions with payload-bound versions and guarded navigation

The authenticated scorekeeper now supports independent game IDs, payload-bound optimistic versions, explicit create/update saves, and guarded workspace transitions. DB list metadata is separated from save authority, while dirty prompts protect voluntary navigation and 401 responses immediately remove private state. Active deletion resets to a clean random ID; profile application remains seat-name-only; guest memory semantics, deferred iframe loading, and the handTai bridge remain intact. The current browser mock and one API identity edge do not yet satisfy the stricter version-binding contract.

Watch for: **confirmed** `online-auth-001` times out before its mocked PUT because it saves a DB-listed ID before loading and binding that payload; **confirmed** a DB payload with an absent internal ID can be normalized to a different workspace ID and lose the envelope’s version binding.

**Verdict**: NEEDS_CHANGES

## High-level view

`listSessionVersions` now serves only list rendering and deletion, while `workspaceVersions` authorizes updates. A fresh random ID saves with `expectedVersion: null`; a GET or successful PUT establishes the workspace version, and list/player refreshes cannot advance it. Save locks the workspace before reading the payload, adopts the PUT response version before refreshing, and leaves both the dirty payload and old binding untouched on 409.

Dirty state gates load, new-session, logout, guest navigation, and `beforeunload`. A 401 bypasses those voluntary guards and clears the token, version maps, account UI, and iframe immediately. Deleting the active DB record clears history and bindings before presenting a clean random-ID workspace, while applying a profile delegates only the selected seat and name.

The server permits an empty payload ID, but the client normalizer replaces one with a random ID. This can turn a loaded-record update into a new-record PUT. The only authenticated browser scenario also predates the list/workspace split in its mocked flow and leaves most new transitions uncovered.

### High — The stricter save guard invalidates `online-auth-001`

**confirmed** — The test publishes `cloud-1` in the session list, installs a host whose current payload is also `cloud-1`, and clicks Save before Load (`scorekeeper-tests.html:570-660`). Refresh writes version 7 only to `listSessionVersions` (`session-scorekeeper-online/app.js:474`), while Save rejects a listed ID that has no payload binding (`session-scorekeeper-online/app.js:597-609`). `savedRequest` therefore stays null and the wait at `scorekeeper-tests.html:653` times out.

Load `cloud-1` before asserting an update, or first save a genuinely fresh ID with `expectedVersion: null` and then load/assert version 7. This blocks a green existing regression run: `run_scorekeeper_tests.py` can launch and execute, but `online-auth-001` cannot pass with the current mock. The 47/47 evidence in `test-results/scorekeeper-latest.json` is inconsistent with this current control flow and does not validate the new guard.

### Medium — GET payload identity is not bound to the envelope identity

**confirmed** — `loadSession` validates the envelope, installs `item.payload`, then stores the version under the requested ID without checking the installed payload ID (`session-scorekeeper-online/app.js:693-699`). The backend rejects only non-empty ID mismatches (`backend/src/main/java/com/onevictoria/mahjong/web/ApiController.java:127-170`), and the host replaces an empty ID with a random one (`session-scorekeeper/app.js:191-194`). The next Save sees that random ID as fresh and sends `expectedVersion: null`, creating a second record rather than updating the loaded record.

Require a non-blank payload ID equal to the route/envelope ID, and defensively verify the normalized payload identity before binding its version client-side.

### 401 teardown cannot be vetoed by a dirty prompt

Dirty checks guard new/load (`session-scorekeeper-online/app.js:663-689`), logout (`session-scorekeeper-online/app.js:781-789`), guest navigation (`session-scorekeeper-online/app.js:797-807`), and `beforeunload` (`session-scorekeeper-online/app.js:835-839`). Non-auth API 401 handling instead calls `clearAuthentication` directly (`session-scorekeeper-online/app.js:319-329`), whose unload path clears versions and removes the iframe (`session-scorekeeper-online/app.js:263-312`). This prevents expired credentials from leaving private workspace state mounted.

After active DELETE, the shell creates a session with `clearHistory: true`, marks it clean, and clears workspace bindings (`session-scorekeeper-online/app.js:708-744`); the host generates its ID with `crypto.randomUUID` when available (`session-scorekeeper/app.js:26,1170-1185`). The deleted ID is therefore not reachable through normal Save or undo paths.

### Medium — The new session state machine is largely untested

**confirmed** — `scorekeeper-tests.html:570-680` is the only authenticated-shell scenario. It does not cover fresh-ID/null-version creation, rebinding from a successful PUT, duplicate-save locking, 409 preservation, refresh isolation, active deletion reset, dirty cancellation, dirty 401 teardown, or seat-only profile application; its host mock also omits `getSessionStatus`, `markSaved`, `createSession`, and `applyPlayerName`.

Add focused transition scenarios. Existing tests still cover memory-only guest behavior (`scorekeeper-tests.html:426-434`), deferred iframe loading (`session-scorekeeper-online/index.html:106`, `session-scorekeeper-online/app.js:413`), and handTai-only transfer (`mahjong-suite/app.js:24-35`), but not the optimistic-version lifecycle.
