# All Tests Rule Alignment Fix Bugfix Design

## Overview

This bugfix will make the complete canonical scoring suite executable and authoritative, align the affected scoring combinations with the supplied Taiwan Mahjong v2.7 amendment dated 05-FEB-2026, and remove only workspace artifacts proven obsolete after validation. The canonical test definitions remain in `test.html`; `build_test.py` remains responsible for generating a self-contained browser test document from `mjConst.js`, `checkHandType.js`, and those canonical definitions.

The fix approach has four coordinated parts:

1. Strengthen the canonical test model so each case can assert required `(name, score)` results and prohibited results, rather than passing on a name-only or permissive prefix match.
2. Diagnose each failing case at the scoring detector or exclusion rule that owns the behavior, then make the smallest rule-based correction. In particular, verify rather than assume the correctness of the pre-existing unverified 嚦咕嚦咕-specific partial change in `checkHandType.js`.
3. Add a Python-driven local runner that builds the standalone page, serves it over loopback HTTP, executes it in an installed Chrome or Edge headless browser with an isolated temporary profile, parses a machine-readable completion record, and exits nonzero on incomplete execution, test failure, test error, or infrastructure failure. This path does not require a globally installed Node.js runtime.
4. After a successful complete run, classify tracked diagnostics and generated files conservatively, remove only artifacts shown to be duplicate, stale, generated, or unused, and retain one organized, reproducible result record.

No scoring change is accepted merely because it makes a test pass. Every changed expectation must be traceable to `台灣牌規則_OV_2.7.docx`, and every implementation change must address an identified detector, score-selection, or exclusion root cause.

## Glossary

- **Bug_Condition (C)**: An execution or repository state in which at least one canonical test fails or errors, an amendment-specific score or exclusion is wrong, the full suite cannot be run reliably without global Node.js, completion evidence is ambiguous, amendment coverage is incomplete, or obsolete artifacts obscure the authoritative result.
- **Property (P)**: The required post-fix state: all canonical tests are discovered and executed, required results are included at exact scores, prohibited results are absent, no test errors occur, and the runner emits an unambiguous successful result.
- **Preservation**: Existing valid scoring outside the amended conditions, especially ordinary non-嚦咕 honor scores, plus canonical tests, source, deployment files, and rule references that must remain unchanged.
- **Canonical suite**: The test definitions in `test.html`. Generated HTML, ad hoc runners, screenshots, and historical text/HTML outputs are not independent test authorities.
- **Exact result**: A result with the expected hand-type name and score, using an explicitly declared matching policy only for genuinely parameterized names such as `純全帶X(...)`.
- **Prohibited result**: A hand type that must not occur in a result set, including `無字` and `無字花` in each v2.7 exclusion case and any wrong-score form of a targeted 嚦咕嚦咕 honor result.
- **F**: The original scoring and test behavior before this bugfix, including the current unverified partial 嚦咕嚦咕 score change.
- **F'**: The validated scoring, test, execution, and cleanup behavior after this bugfix.
- **`detectHandTypes`**: The scoring entry point in `checkHandType.js`; it detects candidate hand types, applies exclusions, applies low-score fallback behavior, and sorts the final results.
- **`EXCLUSION_RULES` / `applyExclusions`**: The centralized rule table and filter in `checkHandType.js` that remove non-stackable hand types, including prefix handling for parameterized names.
- **嚦咕嚦咕 (Ligu)**: The special pair-based hand family whose v2.7 honor-pair additions differ from the ordinary pung-based 小三風, 小三元, and 小四喜 values.
- **Ordinary honor patterns**: Non-嚦咕 小三風, 小三元, and 小四喜, which remain 20, 30, and 80 respectively.
- **Standalone test page**: `test_standalone.html`, generated by `build_test.py`; it is derived output, not a second canonical test source.
- **Authoritative evidence**: A fresh machine-readable result generated by the reliable runner that records discovered, executed, passed, failed, and errored counts, execution path, browser identity, and final status.

## Bug Details

### Bug Condition

The bug manifests when the canonical suite cannot prove complete success, when the v2.7 amended exclusions or 嚦咕嚦咕 values are wrong, or when stale/duplicate artifacts make the source and latest result ambiguous. A test is not considered successful if it merely finds a similarly prefixed name, finds a name at the wrong score, omits an asserted exclusion, or never executes.

**Formal Specification:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type ValidationInput
  OUTPUT: boolean

  scoringDefect :=
       (input.hand qualifiesFor anyOf [斷么, 純全帶么九, 清老頭/清么碰,
                                      缺一門, parameterized純全帶X, 小於五, 缺五]
        AND input.hand hasNoHonors
        AND resultContains(input.result, 無字 OR 無字花))
    OR (input.hand is 嚦咕嚦咕 AND hasPairsOfThreeDistinctWinds(input.hand)
        AND NOT resultContainsExact(input.result, 小三風, 10))
    OR (input.hand is 嚦咕嚦咕 AND hasPairsOfAllThreeDragons(input.hand)
        AND NOT resultContainsExact(input.result, 小三元, 15))
    OR (input.hand is 嚦咕嚦咕 AND hasPairsOfAllFourWinds(input.hand)
        AND NOT resultContainsExact(input.result, 小四喜, 40))

  executionDefect :=
       input.suite.discoveredCount != input.suite.executedCount
    OR input.suite.failedCount > 0
    OR input.suite.errorCount > 0
    OR input.suite.status is ambiguous
    OR input.execution assumesGlobalNode
    OR input.execution is not repeatable

  coverageDefect :=
       NOT coversAllSevenNoHonorExclusions(input.suite)
    OR NOT coversAllThreeLiguHonorValues(input.suite)
    OR NOT coversOrdinaryHonorComparisons(input.suite)

  cleanupDefect :=
       obsoleteArtifactsObscureAuthority(input.repository)
    OR cleanupWouldRemovePreservedMaterial(input.cleanupPlan)

  RETURN scoringDefect OR executionDefect OR coverageDefect OR cleanupDefect
END FUNCTION
```

### Property Predicate

```
FUNCTION expectedBehavior(result)
  INPUT: result of type ValidationResult
  OUTPUT: boolean

  RETURN result.discoveredCount = result.executedCount
     AND result.executedCount = result.passedCount
     AND result.failedCount = 0
     AND result.errorCount = 0
     AND everyCaseIncludesAllExactExpectedResults(result.cases)
     AND everyCaseExcludesAllProhibitedResults(result.cases)
     AND allAmendedScoresMatchTaiwanMahjongV2_7(result.cases)
     AND ordinaryNonLiguScoresArePreserved(result.cases, [20, 30, 80])
     AND result.executionPath doesNotAssume globalNode
     AND result.evidence is machineReadable AND reproducible
END FUNCTION
```

### Examples

- **斷么 exclusion**: A no-honor 斷么 hand is expected to include `斷么(5)` and exclude both `無字(2)` and `無字花(5)`. The current suite can pass after finding `斷么` without proving either exclusion.
- **清老頭/清么碰 exclusion**: An all-terminal hand is expected to include `清么碰(200)` and exclude `無字` and `無字花`, even though the tile set independently satisfies the low-level no-honor predicates.
- **Parameterized exclusion**: A result named `純全帶X(...)` is expected at its rule-derived score while both no-honor bonus names are absent. Prefix matching is permitted only for the declared parameterized family, not as a general fallback for unrelated tests.
- **嚦咕嚦咕 winds**: A valid 嚦咕嚦咕 hand containing pairs of three distinct winds is expected to include `小三風(10)`, not the ordinary `小三風(20)` and not a duplicate wrong-score entry.
- **嚦咕嚦咕 dragons**: A valid 嚦咕嚦咕 hand containing pairs of 中, 發, and 白 is expected to include `小三元(15)`, while a non-嚦咕 hand with the ordinary two-pungs-plus-pair structure remains `小三元(30)`.
- **嚦咕嚦咕 four winds**: A valid 嚦咕嚦咕 hand containing all four wind pairs is expected to include `小四喜(40)`, while a non-嚦咕 three-pungs-plus-pair hand remains `小四喜(80)`.
- **Incomplete execution**: If 120 tests are discovered but only 119 execute, the run fails even when those 119 pass. Browser startup failure or a page-level JavaScript exception is an error, not a zero-test pass.
- **Cleanup edge case**: `test_standalone.html` may be removed from version control only after proving it is reproducibly generated and unused by deployment. `test.html`, source JavaScript, GitHub Pages configuration, `.kiro` specifications, and `台灣牌規則_OV_2.7.docx` are never cleanup candidates.

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Non-嚦咕 小三風 continues to score 20.
- Non-嚦咕 小三元 continues to score 30.
- Non-嚦咕 小四喜 continues to score 80.
- Hands outside the amendment conditions continue to produce the same valid names, scores, exclusions, multiplicity, and ordering established by the canonical suite and supplied rules.
- Every valid existing canonical test remains enabled and executes; tests are not deleted, skipped, selectively omitted, or weakened to manufacture a pass.
- `test.html` remains the canonical test-definition source, and `build_test.py` continues to derive the standalone browser document from it.
- Source files (`mj.html`, `mj.css`, `mj.js`, `mjConst.js`, `checkHandType.js`), canonical tests, deployment configuration, specification files, and the supplied rule document remain preserved.
- Useful non-generated support and the latest reproducible validation evidence remain available in an organized form.

**Scope:**
All inputs outside the formal amended scoring conditions must be unaffected. This includes:
- Ordinary non-嚦咕 wind and dragon structures.
- Existing scoring combinations unrelated to no-honor exclusions or 嚦咕 honor pairs.
- UI and deployment behavior; the fix is confined to scoring rules, test infrastructure, and confirmed artifact cleanup.
- Canonical test definitions not shown by investigation to contain an invalid setup or rule expectation.
- Files whose purpose or deployment relationship cannot be proven obsolete.

Cleanup is deny-by-default: uncertainty means preserve. A file becomes removable only after its generated/diagnostic/duplicate role and lack of source, test, deployment, rule-reference, or unique-support value are demonstrated.

## Hypothesized Root Cause

Based on the completed requirements and repository inspection, the most likely issues are:

1. **Weak Test Oracle**: `test.html` currently accepts broad prefix/name-only matches after an exact score match fails.
   - A test may pass when a related name exists at the wrong score.
   - Existing cases mainly prove inclusion and do not encode prohibited output, so v2.7 non-stacking rules can regress unnoticed.
   - Error counting is conflated with failure counting, and completion is shown only in browser-rendered text.

2. **Incomplete Exclusion Validation**: The central `EXCLUSION_RULES` table already contains apparent entries for the seven amended families, including prefix handling for `純全帶X`, but those entries have not been conclusively exercised against exact final result sets.
   - The defect may be an omitted/incorrect detector name, a prefix interaction, ordering before `applyExclusions`, or an invalid test fixture rather than a missing table row.
   - Changing scores or fixtures before inspecting candidate results and post-exclusion results would hide the root cause.

3. **Unverified Ligu-Specific Branching**: `checkHandType.js` has a pre-existing partial change that counts honor pairs inline and selects special scores before ordinary wind/dragon branches.
   - The change is not covered by canonical amendment tests and therefore cannot be treated as correct.
   - It repeatedly recomputes Ligu status and embeds pair-count classification inside `detectHandTypes`, making boundary behavior and ordinary-score preservation harder to reason about.
   - Exact pair counts, quads, the winning tile, and the current `isLiguligu`/`isEightPairs` semantics may cause false positives or false negatives unless valid fixtures exercise them.

4. **Non-Authoritative Execution Paths**: `run_tests.js` requires Node, while direct prior browser headless attempts were unreliable.
   - `build_test.py` generates a synchronous standalone page but its current output lacks a strict, machine-readable completion contract and separate error count.
   - Historical HTML/text outputs and screenshots can look successful without proving all currently discovered tests ran.
   - Browser invocation through `file://`, shared profiles, absent timeouts, and output scraping from presentation text are likely sources of nondeterminism.

5. **Artifact Accumulation**: Tracked debug pages/scripts, screenshots, repeated output/result files, legacy runners, and generated standalone content represent multiple historical execution attempts.
   - Their names do not identify a single authority or freshness guarantee.
   - Some may still be uniquely useful, so cleanup must follow reference/deployment inspection and successful replacement, not filename-based bulk deletion.

## Correctness Properties

Property 1: Bug Condition - Taiwan Mahjong v2.7 Amended Scoring

_For any_ valid winning hand where the scoring bug condition holds, the fixed `detectHandTypes` pipeline SHALL include every rule-required result at its exact v2.7 score and SHALL exclude every prohibited result: all seven listed no-honor combinations exclude `無字` and `無字花`, and qualifying 嚦咕嚦咕 honor-pair hands score 小三風 at 10, 小三元 at 15, or 小四喜 at 40 as applicable.

**Validates: Requirements 2.2, 2.3, 2.4, 2.5, 2.6, 2.7, 2.8, 2.9, 2.10, 2.11, 2.14**

Property 2: Preservation - Non-Amended Scoring and Canonical Tests

_For any_ hand where the amended scoring bug condition does NOT hold, F' SHALL produce the same valid hand-type names, scores, exclusions, multiplicity, and ordering as F, including ordinary non-嚦咕 小三風 at 20, 小三元 at 30, and 小四喜 at 80; every valid pre-existing canonical test SHALL remain enabled and strongly asserted.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.5**

Property 3: Complete Suite - No Silent Omission or Error

_For any_ canonical suite generated from `test.html`, the test system SHALL execute every discovered case exactly once and SHALL report success only when `discovered = executed = passed`, `failed = 0`, and `errors = 0`; exact expected inclusions and declared prohibited exclusions SHALL both participate in each case verdict.

**Validates: Requirements 2.1, 2.13, 2.14, 3.5**

Property 4: Reliable Execution - No Global Node Assumption

_For any_ supported local environment with Python and at least one detected Chrome-family browser (Chrome or Edge), including an environment without global Node.js, the local runner SHALL build and serve the canonical suite, execute it in an isolated browser process, distinguish test failure from infrastructure failure, emit machine-readable evidence, and return an unambiguous process exit status.

**Validates: Requirements 2.12, 2.13**

Property 5: Conservative Cleanup - Preserve Authoritative Material

_For any_ repository file considered during cleanup, the cleanup SHALL remove it only if it is confirmed unused and duplicate, stale, generated, or diagnostic; otherwise it SHALL preserve the file, with unconditional preservation for source, canonical tests, deployment configuration, specifications, and the supplied v2.7 rule reference.

**Validates: Requirements 2.15, 3.6, 3.7**

## Fix Implementation

### Changes Required

Implementation must proceed in evidence order: establish a strict runner and surface counterexamples first, diagnose each failure, apply scoring/test-fixture corrections, rerun the complete suite, and only then clean artifacts.

**File**: `test.html`

**Functions / structures**: `add`, canonical test definitions, `runAllTests`

**Specific Changes**:
1. **Explicit assertion schema**: Extend each canonical case to declare exact expected results and optional prohibited results.
   - Represent required results as `(name, score)` pairs rather than deriving the sole expectation from a display label.
   - Allow a declared matcher only for genuinely parameterized names; remove reciprocal/general prefix fallback and name-only success.
   - Permit assertions that a name is absent entirely and that a targeted name occurs only at the permitted score/multiplicity.
2. **Amendment matrix**: Add focused cases for 斷么, 純全帶么九, 清老頭/清么碰, 缺一門, parameterized 純全帶X, 小於五, and 缺五.
   - Each fixture must be a valid hand, include the target result at its exact score, and prohibit both `無字` and `無字花`.
   - If a setup unintentionally qualifies for another overriding pattern, correct the setup rather than weakening the assertion.
3. **Ligu and ordinary comparison matrix**: Add valid Ligu cases for three wind pairs, three dragon pairs, and four wind pairs, plus separate non-Ligu ordinary comparisons at 20/30/80.
   - Prohibit the same targeted name at its ordinary/wrong score in each Ligu case.
   - Assert the Ligu base result when required by the rule so a coincidental honor result cannot pass an invalid fixture.
4. **Complete result accounting**: Track `discovered`, `executed`, `passed`, `failed`, and `errors` separately, preserving per-case diagnostic details.
   - A setup/detector exception increments `errors` and `executed` and cannot be reported as a normal assertion failure.
   - Emit a stable machine-readable completion payload in the DOM in addition to the human table.
   - Support an explicit auto-run mode used by the local runner while retaining manual browser execution.

**File**: `build_test.py`

**Function / responsibility**: standalone browser-test generation

**Specific Changes**:
1. **Canonical derivation**: Continue sourcing definitions from `test.html`; do not copy amendment cases into a second source.
2. **Harness parity**: Generate the standalone page from the same assertion and reporting semantics used by the canonical page so manual and automated verdicts cannot diverge.
3. **Fail-fast generation**: Reject missing/duplicate extraction markers and malformed or empty test-definition extraction with a nonzero exit.
4. **Deterministic output**: Ensure generated output has UTF-8 content, a stable completion element, and no stale embedded result.
5. **Derived-file policy**: Treat `test_standalone.html` as reproducible generated output. Its tracking/retention decision occurs only after reference and deployment checks.

**File**: `run_tests.py` (new local test orchestrator; exact name may be adjusted only to avoid a proven repository conflict)

**Functions / responsibilities**: build, browser discovery, temporary HTTP serving, browser execution, result parsing, evidence writing, exit status

**Specific Changes**:
1. **No Node dependency**: Invoke the available Python interpreter and `build_test.py`; do not call `run_tests.js` or assume `node` is globally resolvable.
2. **Browser discovery**: Search explicit configuration first, then `PATH`, then standard Windows Chrome and Edge install locations. Report all attempted candidates when none can run.
3. **Reliable browser isolation**:
   - Serve the repository/test page from a loopback-only HTTP server on an ephemeral port instead of relying on `file://` behavior.
   - Launch one detected browser in headless mode with a fresh temporary user-data directory, deterministic flags, captured output, and a hard timeout.
   - Use the alternate installed browser only for browser/infrastructure startup failure, not to mask a genuine test failure.
4. **Machine contract**: Parse only the dedicated completion payload and require a matching schema/version, success status, and count invariant. Missing, malformed, duplicate, or timed-out completion is an infrastructure error.
5. **Exit semantics**: Return zero only for complete success; use nonzero statuses for test failures/errors, build failure, no usable browser, timeout, and malformed evidence.
6. **Fresh evidence**: Write one organized result such as `test-results/latest.json` atomically after each complete run.
   - Include timestamp, source revision or source hashes, execution command/path, browser name/version, discovered/executed/passed/failed/error counts, and failing-case details.
   - Mark unsuccessful runs as unsuccessful; never preserve an old pass as the apparent result of a new failed/incomplete run.
   - Avoid embedding machine-specific temporary profile paths or other non-reproducible noise.

**File**: `checkHandType.js`

**Functions / structures**: `detectHandTypes`, `EXCLUSION_RULES`, `applyExclusions`, Ligu classification helpers, wind/dragon detectors

**Specific Changes**:
1. **Counterexample-first diagnosis**: Before altering scoring, capture the pre-exclusion candidates and final result for every amendment fixture.
   - If the expected target is not detected, fix the owning detector or fixture.
   - If `無字`/`無字花` survives despite a target, fix the exact exclusion name/prefix rule or application ordering.
   - Do not add broad exclusions that affect unrelated hands.
2. **Centralized v2.7 exclusions**: Keep no-honor non-stacking behavior in `EXCLUSION_RULES`/`applyExclusions` unless investigation proves that model insufficient.
   - Verify aliases (`清老頭` in the rule document versus emitted `清么碰`) and parameterized `純全帶X(...)` names explicitly.
   - Apply exclusions to the completed candidate set once, preserving existing deterministic ordering.
3. **Validate and refactor the partial Ligu change**: Treat the current inline pair-count code as an unverified hypothesis.
   - Establish valid red tests against the unfixed/baseline behavior.
   - Prefer one structured Ligu classification computed once per detection, with explicit distinct wind-pair and dragon-pair counts derived from the full winning hand under validated pair semantics.
   - Select 10/15/40 only when the hand is valid Ligu and the exact amendment condition holds; otherwise defer to unchanged ordinary detectors and values.
   - Prevent duplicate targeted names or simultaneous special and ordinary values.
4. **Minimal scoring corrections**: For other complete-suite failures, change production logic only after identifying a rule mismatch. If the implementation follows v2.7 and a fixture is invalid, repair the fixture while preserving the intended coverage.

**Files**: `.gitignore`, stale/generated/diagnostic candidates, and retained evidence location

**Specific Changes**:
1. **Inventory before deletion**: Classify each candidate by provenance, references, deployment use, unique diagnostic value, and reproducibility.
2. **Likely candidates requiring confirmation**:
   - Generated/stale results: `test_standalone.html`, `test_output*.html`, `full_output*.html`, `test_results.txt`, `results*.txt`, `failures.txt`.
   - Diagnostics: `debug*.html`, `debug_test.js`, and `*_screenshot*.png`.
   - Duplicate/legacy runners: `run_tests.js`, `run_tests_hta.hta`, `test_runner.html`, `check_tests.py`, and `check_tests2.py` after the Python/browser runner proves it supersedes their useful behavior.
3. **Conservative decision rule**: A listed candidate is not automatically deleted. Preserve any file referenced by source, canonical tests, GitHub Pages/deployment, documentation that remains authoritative, or a unique reproducible workflow.
4. **Protection and organization**: Ignore reproducible transient build/output files where appropriate; retain the single latest evidence record in a clearly named location if requirements call for checked-in evidence.
5. **Unconditional preservation**: Preserve application source, `test.html`, the validated runner/generator, `.github` deployment files, `.kiro` specifications, license and useful documentation, and `../台灣牌規則_OV_2.7.docx`. Do not edit or relocate the supplied rule document as part of cleanup.

## Testing Strategy

### Validation Approach

Validation follows three gates. First, run strict exploratory tests against the current/unfixed behavior to surface real counterexamples and confirm or refute each root-cause hypothesis. Second, apply minimal fixes and run exact fix checks for every amended condition. Third, run preservation and full-suite checks, record fresh evidence, and perform cleanup only after all scoring and execution gates pass.

A test run is authoritative only if the runner itself exits successfully and its machine-readable counts prove `discovered = executed = passed`, with zero failures and zero errors. Screenshots and old output files are never pass evidence.

### Exploratory Bug Condition Checking

**Goal**: Surface counterexamples before changing scoring logic, verify that fixtures are valid, and distinguish detector defects, exclusion defects, oracle defects, and execution defects. If evidence refutes a root-cause hypothesis, re-hypothesize before editing production logic.

**Test Plan**:
1. Add or temporarily execute strict assertion forms against current behavior without accepting permissive prefix/name-only fallback.
2. For each amendment fixture, capture raw detected candidates before exclusions and final results after exclusions.
3. Execute the suite through the proposed Python/HTTP/browser path and intentionally exercise malformed completion and browser timeout handling.
4. Record the current behavior of ordinary non-Ligu comparison fixtures before changing the Ligu branch.
5. Compare rule-sensitive expectations to the supplied v2.7 reference; never infer correctness solely from existing outputs.

**Test Cases**:
1. **Seven Exclusion Counterexamples**: One valid hand each for 斷么, 純全帶么九, 清么碰, 缺一門, parameterized 純全帶X, 小於五, and 缺五; assert target inclusion and `無字`/`無字花` absence (at least one may fail or expose an invalid setup on unfixed code).
2. **Ligu Wind Pairs**: Three distinct wind pairs require `小三風(10)` and prohibit `小三風(20)` (expected to fail without a correct special branch).
3. **Ligu Dragon Pairs**: Three dragon pairs require `小三元(15)` and prohibit `小三元(30)`.
4. **Ligu Four Wind Pairs**: Four wind pairs require `小四喜(40)` and prohibit `小四喜(80)`.
5. **Ordinary Baseline**: Non-Ligu structures produce 20, 30, and 80 before and after the fix.
6. **Wrong-Score Oracle Probe**: Supply a result with the expected name at a wrong score and verify the strict harness fails it; this demonstrates the current permissive oracle defect.
7. **Incomplete Runner Probe**: Simulate discovered/executed mismatch, page exception, missing completion payload, and browser timeout; each must produce a nonzero result.

**Expected Counterexamples**:
- A target name at the wrong score can pass the current name-only fallback.
- A target result can pass without checking that `無字` or `無字花` was removed.
- The partial Ligu branch may misclassify one or more valid pair structures or may preserve the wrong ordinary/special value.
- Direct browser output may lack a trustworthy completion marker or complete counts.
- Possible causes include permissive assertion logic, fixture overlap, emitted-name/exclusion-key mismatch, incorrect Ligu pair classification, or unreliable browser invocation.

### Fix Checking

**Goal**: Verify that every input satisfying the bug condition produces exact v2.7 behavior and that the full runner detects any deviation.

**Pseudocode:**
```
FOR ALL input WHERE isBugCondition(input) DO
  result := validateWithFixedPipeline(input)
  ASSERT expectedBehavior(result)
END FOR
```

**Checking details**:
- For every no-honor amendment case, assert the exact target `(name, score)` and separately assert absence of `無字` and `無字花`.
- For every Ligu amendment case, assert valid Ligu classification, exact special `(name, score)`, no same-name wrong score, and no duplicate targeted result.
- Assert suite count invariants and nonzero exits for deliberately failing, throwing, incomplete, and malformed runs.
- Run twice from clean temporary profiles to demonstrate repeatability and freshness of evidence.

### Preservation Checking

**Goal**: Verify that inputs outside the amendment conditions and protected repository material retain their behavior.

**Pseudocode:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  ASSERT normalize(F(input)) = normalize(F'(input))
END FOR

FOR ALL file IN repository DO
  IF NOT confirmedObsolete(file) OR isProtected(file) THEN
    ASSERT file is preserved
  END IF
END FOR
```

**Testing Approach**: Property-based and differential testing is recommended because scoring inputs have many overlapping predicates and exclusions. Generate valid bounded tile/state combinations, compare normalized pre-fix and fixed outputs outside the amended domain, and retain counterexample seeds. Because the project has no established property-testing dependency, implement deterministic generators in the existing browser harness or use Python orchestration without adding a package unless a dependency is explicitly approved.

**Test Plan**: Capture baseline ordinary honor cases and the full valid canonical suite before production changes. After the fix, compare unaffected outputs, verify all pre-existing test identities remain present and executed, and audit cleanup candidates against references and protected-path rules.

**Test Cases**:
1. **Ordinary Honor Preservation**: Verify non-Ligu 小三風(20), 小三元(30), and 小四喜(80).
2. **Unrelated Scoring Preservation**: Compare names, scores, exclusions, multiplicity, and order for deterministic generated hands outside amended predicates.
3. **Canonical Suite Integrity**: Compare stable test IDs before/after; no unexplained deletion, skip, duplicate, or unexecuted case is allowed.
4. **Manual Runner Preservation**: Verify `test.html` still runs interactively while auto-run emits the same verdict.
5. **Deployment Preservation**: Confirm application and GitHub Pages entry/configuration references remain valid after cleanup.
6. **Cleanup Dry Run**: Produce the candidate classification before deletion and fail the cleanup check if a candidate is referenced, non-reproducible, protected, or uncertain.
7. **Evidence Freshness**: Verify a failed later run cannot leave an older passing record presented as current.

### Unit Tests

- Exact assertion matcher: correct `(name, score)` passes; wrong score, broad prefix, missing required result, prohibited result, and duplicate targeted result fail.
- `applyExclusions`: each of the seven amended target names removes both `無字` and `無字花`; unrelated result sets remain unchanged.
- Parameterized `純全帶X(...)` exclusion matching works only for the intended family.
- Ligu classifier recognizes valid three-wind-pair, three-dragon-pair, and four-wind-pair cases and rejects non-Ligu/near-miss structures.
- Score selection yields 10/15/40 for Ligu and 20/30/80 for ordinary comparison structures.
- Result accounting separates assertion failures, exceptions, and infrastructure errors and enforces discovered/executed equality.
- Browser completion parser rejects missing, duplicate, malformed, stale, and internally inconsistent payloads.
- Cleanup classifier protects all required categories and defaults uncertain files to preserve.

### Property-Based Tests

- Generate valid Ligu pair distributions and assert honor special scores exactly when the relevant distinct-pair condition holds, with no ordinary-score duplicate.
- Generate valid no-honor hands that qualify for each amended target and assert `無字`/`無字花` exclusion regardless of unrelated allowed additions.
- Generate valid non-amended scoring states and differentially compare normalized F and F' outputs, retaining seeds for any mismatch.
- Generate test-result count tuples and assert runner success if and only if all count invariants and zero failure/error conditions hold.
- Generate repository classification records and assert protected, referenced, unique, or uncertain files are never selected for deletion.
